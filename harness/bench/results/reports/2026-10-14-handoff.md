## 1. The mission

Make umbral dramatically faster using honest measurement, targeting **25,000+ RPS**, by first building a trustworthy benchmark rig and then optimizing the framework. Operator's binding constraints, which do not bend:

- **No `unsafe` Rust.** Spec locked decision #8 — out of scope, not deferred. A gap only `unsafe` could close is reported with its measured cost.
- **Do not remove work the application has to do.** Security headers, CSRF, sessions, real auth, real durable writes all stay in the measured path. A change that only wins by deleting them is the exact failure the rig exists to catch.
- **Never wipe a database or migration files** to make a failure go away. The declare → migrate → change → migrate loop *is* the product; existing rows are the test, not an obstacle.
- **Never `git stash`.** The operator works on several things in parallel and their dirty tree is state.
- **Do not touch the dev server** the operator runs for examples.
- Run in the **fixed-resource silo**; k6 outside Docker; **5-minute holds**.

### What this settles

**Middleware is not where the work is, and cannot close the gap.** Deleting the entire middleware chain buys ~57 µs of 1088, about **5%**. The target needs roughly **6×**. The v1 rig's shape hypothesis — database dominates by orders of magnitude, middleware is nearly free — is **confirmed**, on a rig that holds up.

**Every optimization cycle must target the database bucket.**

### Two limits on what the ledger can say

- **`query_build` is 0 and the `sql` block is empty `[]`.** sqlx gives no per-statement attribution on SQLite, so the 905 µs **cannot be split by query**. That split is the prerequisite for naming a Cycle 1 target.
- **"Database" is ORM wall time, not time inside SQLite** (`db_source: orm_wall` on every record). A meaningful part of the 905 µs is therefore **framework code that can be optimized**, not a C library.
- **It is a FLOOR for prod, not an estimate.** The instrumented binary mounts `CookieStore` while prod mounts `DbStore`, and in this tree the instrumented binary's cookie store **cannot authenticate the pooled cookies at all** (raw rotated UUID against an AEAD store). Prod's real session read appears nowhere in the ledger — it is inside the database bucket. So prod's bucket is *bigger* than 905 µs.

## 5. The defect that paused everything

`harness/bench/k6/lib.js:107`:

```js
const session = sessions[(__VU - 1) % sessions.length];
```

Pool **200**, VUs **2,500** → each session identity shared by **12–13 concurrent clients**. Meanwhile `harness/bench/workload.md:33` states the opposite intent:

> *"VUs are pinned to one pooled session each, so a VU's traffic is one coherent user rather than a new identity per call."*

`BENCH_SESSION_POOL_SIZE` defaults to 200 (`bench-prod.rs:39`), never revisited when VUs went to 2,500. No rationale for 200 exists anywhere. `README.md:113` bakes it into the documented recipe.

**Why it is not cosmetic:** the session read lives inside the 905 µs database bucket, so this contaminates **83% of the measured time**, in the direction that **flatters `DbStore`** — the exact arm the session-store comparison exists to evaluate. Read latency barely moves (log₂(200)≈7.6 vs log₂(2500)≈11.3 page descents); the *working set* does (200 resident session rows vs ~2,500, on a page cache shared with the whole feed workload, plus last-seen writes touching 200 rows instead of 2,500).

**A second hole of the same class the rig already closed for the mix:** the pool size is **not recorded in any result file** (the `session` block carries store/cookie/ttl/max-age only) and `compare.sh` refuses across `mix`, `dataset_scale`, `cpuset` — but **not** across a pool-size change. A rebuilt pool would diff happily against a 200-pool baseline.

## 7. The operator's directive — the order of work

Stated 2026-10-14, verbatim intent: *"fix the rig first, then re-baseline on postgres. Just make sure that we do what actual users do. Then instead of 2500VUs, we need to hit the number up to see if there are any rps increases. Then from there, we need to measure the framework's own bottlenecks and then start fixing them. First things first, only run a single test, not 3 with the fix and vus increase."*

1. **Finish the rig fix** (§6). Verify behaviour, not just compilation.
2. **Re-baseline on Postgres** — **ONE hold.** Postgres is the product's stated primary backend ("Postgres-first, SQLite for tests"), and the old Postgres baseline was taken on the defective pool, so it is now stale.
3. **Raise the VUs** to find where RPS stops rising — **ONE run per level**, not three. Target ramp 2,500 → 5,000 → 10,000. This is the first measurement that can answer "how fast can it go", because at 2,500 VUs RPS is the think time expressed as a rate. Saturation is estimated near ~7,350 VUs, so the ramp should carry past it.
4. **Split the database bucket by query** — the prerequisite for naming an optimization target.
5. **Then begin optimization cycles**: one change → report → next, each justified from a ledger bucket.

**Single runs are the explicit instruction.** Do not repeat a hold three times to make it look settled.

## 8. Traps that have already bitten us

- **The bare `$?`.** Capture k6's exit code *immediately*; by the time `record.sh` runs, `$?` belongs to `wait` and the sampler exits 0 — a failed threshold would be filed as `passed`. Correct flow is in `harness/bench/results/README.md`.
- **`compare.sh`'s verdict lines are a change detector, not evidence of a change.** On this host its 20% p99 limit sits exactly on the noise floor.
- **A win smaller than the run-to-run spread is not a win.** Report it as undemonstrated. A null result is a result.
- **Never quote a cross-backend delta.** SQLite compares to SQLite, Postgres to Postgres. (This was violated once already — a draft Postgres report derived a "1.2% network cost" from SQLite-vs-Postgres. The real figure was 0.15%, inside SQLite's own spread, supporting nothing.)
- **State an explicit stop condition in every measurement dispatch.** "Three holds" without "and no more" turned a 45-minute task into 2½ hours.
- **Poll the results directory; do not wait on a subagent notification.** Result files are written the moment a hold ends, long before the task reports. `harness/bench/results/*.json`.
- **`?mode=rwc` is required** in the SQLite URL (sqlx opens read-only otherwise), and `UMBRAL_SECRET_KEY` is required in a release build (it defaults to `Environment::Prod`, which refuses the dev key).
- **The silo's cpuset is `0,2,4,6`** — four *distinct physical* P-cores on this i7-13700H. `0-3` would grant two.
- The host is noisy: a Chrome renderer was pegging a core during the Postgres series. **Quiet the host before trusting any tail measurement.**

## 9. Open decisions awaiting the operator

1. **What to do about the noise floor.** Recommended but not yet approved: quiet-host gate, refuse to call sub-noise movements wins, and raise `compare.sh`'s limits above the measured floor.
2. **Whether to re-run the SQLite baseline too**, now that the rig is changing. Postgres is the priority per §7; SQLite will be stale in the meantime.
3. **Whether to model anonymous traffic.** The mix authenticates 100% of requests, which is *heavier* than real traffic (no logged-out visitors or crawlers). That is conservative and safe, and changing it would make numbers look better without the framework being faster — so the recommendation is to keep it and state it as a deliberate choice.

## 11. One-paragraph summary

The rig is trustworthy now — 0.098% RPS spread, a verified silo, a results store that refuses incomparable diffs — and it has already paid for itself twice: it found a migration bug that silently corrupted SQLite indexes, and it produced a layer ledger showing **83% of server time is the database bucket against ~57 µs of real middleware**. That kills the idea that middleware tuning can reach 25,000 RPS (the whole chain is ~5%; the target needs ~6×) and points every remaining cycle at the ORM's database access. Before optimizing, two things must happen: the session-pool defect must be fixed, because it biases that same 83% in favor of the status quo; and the VU count must be raised, because at 2,500 VUs RPS is measuring the workload's think time rather than the framework's capacity. The rig fix is halfway done and checkpointed at `fea2ee32`.
