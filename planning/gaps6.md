7. [ ] **Materialized models / computed fields should auto-refresh when their source tables change** — today a denormalized or computed value (a projection over another table, a cached aggregate, a materialized view backing a model) goes stale silently whenever a related row is inserted / updated / deleted, and the framework offers no way to keep it current except asking the developer to *remember* to recompute it at every write site. That "remember to refresh everywhere" burden is a genuine UX crux: it's the classic cache-invalidation trap, it's easy to get wrong, and a missed call site produces wrong data with no error. Consumers already hit this — the web3clubs backend's `payment` field is a projection over `RSVP` (see `project_web3clubs_fc_backend`), exactly the shape that needs invalidation. The framework should own the refresh so the declaration site is the *only* place the dependency is expressed.

    **The right seam is the existing signals layer, not per-call-site code.** umbral already has post-save / post-delete signals with `signal_skip` and a signal-lock (shipped under the `audit_2` and `gaps3 #29` work). A materialized field / model should be able to **declare its source table(s)**, and the framework wires create/update/delete signals on those sources to trigger the recompute — dependency inversion, so the source table never names the derived one. This keeps it consistent with "the ORM is the single database interface" (recompute goes through the ORM, works on both backends) and with the plugin contract (invalidation is a framework capability, not app glue). Contrast with the alternatives: a Postgres `MATERIALIZED VIEW` + `REFRESH` is PG-only and can't be modelled at the row level (violates the Postgres-first-but-SQLite-for-tests rule), and a DB trigger is backend-specific and invisible to the migration/model layer — both push behaviour out of the ORM where a plugin author can't reach it.

    **Open design questions** (this entry is the *problem statement*; the design needs brainstorming before it's built): (a) declaration surface — a `#[derive(Model)]` attribute naming source models + a recompute closure, vs. a distinct `Materialized`/`Computed` field type, vs. a builder registration; (b) refresh strategy — eager (recompute inside the source write's transaction, correct but couples latency) vs. deferred (enqueue via `umbral-tasks`, decoupled but eventually-consistent) — likely a per-field choice; (c) partial vs. full recompute for aggregates over large source sets; (d) cycle detection when materialized models depend on each other; (e) whether this is a first-class core ORM feature or belongs alongside the heavy-relations aggregates epic (`docs/specs/orm-heavy-relations-epic.md`), since a cached `annotate_count` is one instance of the same problem.

    **Scope (indicative, pending design):** `crates/umbral-core/src/orm/` (the field/model declaration + the signal wiring for source-table invalidation), `crates/umbral-macros/src/lib.rs` (if the surface is a derive attribute), the signals module (register source→derived recompute handlers), optional `umbral-tasks` integration for deferred refresh, behavioral tests (insert/update/delete a source row, read the derived model back, assert it reflects the change without any manual refresh call — surface and deep/aggregate cases), and a `documentation/docs/v0.0.1/orm/` page. Larger than the other gaps6 entries; **start with `superpowers:brainstorming` on the declaration surface + refresh strategy before writing a spec.**

[ ] **Framework scaling should be a default runtime posture, not per-app infrastructure wiring** — Umbral already has the raw pieces for production scale (database pool settings, `DatabaseRouter`, DB-backed tasks, Redis-capable realtime/cache/sessions, readiness/drain hooks), but a developer still has to remember how to assemble them in each app: open pools manually, choose shared-state backends, run workers and beat, wire Redis, think about read replicas, add durable side effects, and avoid unbounded admin/API surfaces. That makes scaling an opt-in checklist instead of a framework default. The framework should own the production topology through a runtime profile / preset layer so app code can stay focused on models, routes, and plugins.

    **Recommended design:** introduce a `RuntimeProfile` plus `PlatformPreset` / expanded `EnterprisePreset`, with an async boot path (`App::from_env()` or `AppBuilder::build_runtime().await`) that opens configured databases automatically, installs the router, applies pool settings, and keeps explicit `.database(...)` as an override. In production/platform profiles, `UMBRAL_REDIS_URL` should automatically select Redis-backed cache, sessions, realtime, and distributed throttling; missing shared state in a multi-replica deployment should be a system-check error or hard warning. Generated deployment/topology should expose explicit `web`, `worker`, and `beat` roles rather than making each app author remember the operational shape. See the companion plan in `planning/framework-scaling-by-default.md`.

    **Scope:** `crates/umbral-core/src/app.rs` (async boot / preset hook), `crates/umbral-core/src/settings.rs` and `src/db.rs` (runtime profile + automatic pool opening), `crates/umbral-core/src/db/router.rs` (first-class replica router), `crates/umbral-cli/src/scaffold.rs` and deployment generation (web/worker/beat topology), `plugins/umbral-tasks` (worker concurrency, heartbeats, required-worker checks), `plugins/umbral-rest` throttles (distributed backend), `plugins/umbral-realtime`, `plugins/umbral-cache`, `plugins/umbral-sessions`, `plugins/umbral-health`, and docs/tests. Acceptance: a new production app can run multiple web replicas without changing app code; unsafe process-local fallbacks warn/fail under production profiles; Redis/read-replica/task topology can be driven from settings; dev remains simple and single-process by default.

11. [ ] **`RedisBackend` tag index is not pruned on delete/clear/retag (no reverse index)** — `MemoryBackend` and `SqliteBackend` (see `plugins/umbral-cache/src/lib.rs::MemoryState::untag` and `SqliteBackend::delete`/`clear`/`set_tagged`) prune a key out of every tag set it belonged to whenever the key is deleted, the cache is cleared, or the key is re-tagged, so a stale `(tag, key)` entry can never survive to wrongly evict a reused key name later. `RedisBackend::set_tagged`/`bust_tag` (added for Task 4, feature-gated behind `redis`) do NOT have this property: Redis has no cheap key→tags reverse index, so `delete`/`clear`/a re-`set_tagged` under a different tag set leave the key's OLD `utag:<tag>` membership(s) in place. Concretely: `set_tagged("k", ..., tags=["a"])` then later `set_tagged("k", ..., tags=["b"])` (or `delete("k")` + a fresh untagged `set("k", ...)`) leaves `k` still a member of Redis set `utag:a`; a later `bust_tag("a")` then `DEL`s the live (differently-tagged, or freshly untagged) key `k` even though it is no longer conceptually tagged `"a"`. This is an accepted, honest divergence for v0 — Redis relies on TTL expiry plus "the common case re-tags with an overlapping/refreshed tag set" rather than exact pruning — not a silently-swallowed bug. Recommended fix (when picked up): maintain a per-key reverse-index set (`ukeytags:<key>` listing that key's current tags) so `delete`/`clear`/`set_tagged` can `SREM` the key out of its old tag sets before applying the new ones, mirroring `SqliteBackend`'s `DELETE FROM umbral_cache_tag WHERE key = ?` prune step, at the cost of one extra round-trip per tagged write. Scope: `plugins/umbral-cache/src/lib.rs` (`RedisBackend::set_tagged`/`bust_tag`/`delete`/`clear`), `plugins/umbral-cache/tests/tagged_redis.rs` (extend with retag/delete-then-reuse cases once fixed, mirroring `tagged_sqlite.rs`'s `sqlite_retag_drops_key_from_its_old_tag_set` / `sqlite_delete_prunes_the_key_from_the_tag_index`).

12. [ ] **`media_access_cached` has a cache miss-compute/bust write-skew race** — the cached resolver in `plugins/umbral-storage/src/lib.rs::media_access_cached` reads the cache, and on a miss runs the developer's closure (the DB work) and only stores `key → bool` (plus its tags) AFTER the closure resolves. If a revocation's `bust_tag` (fired by `media_invalidate_on` off a `post_save`/`post_delete` signal) lands in that window — between the request's cache-miss read and its store — the just-computed, now-stale `allow` is written to the cache *after* the bust and survives until the next TTL expiry, even though the source row that should have revoked it already changed. This is bounded, not unbounded: the security envelope holds because the decision still expires at TTL (default 60s), so the window is "up to one TTL of staleness on an unlucky race," not indefinite staleness. Not fixed here because it needs either a generation counter (store only if the tag's generation hasn't advanced since the read) or a store-time re-check against the bust log, both of which are real design work, not a doc/test fix. Scope when picked up: `plugins/umbral-storage/src/lib.rs` (`media_access_cached`), likely also `plugins/umbral-cache/src/lib.rs` (a generation-aware `set_tagged_bool` variant, or a `bust_tag` sequence counter the store path can check against).

13. [ ] **`media_access_cached`'s cache key delimiter (`:`) is not injective in caller/file-key content** — `format!("mediaacc:{key}:{caller_id}")` in `plugins/umbral-storage/src/lib.rs::media_access_cached` assumes `key` (the file key) and `caller_id` (`Identity::user_id()` or `"anon"`) never themselves contain `:`. If either does, two distinct `(key, caller_id)` pairs can collide on the same formatted string — e.g. `key="f", caller_id="x:y"` renders identically to `key="f:x", caller_id="y"`. Practically unreachable today: `caller_id` comes from umbral-auth's PK, which is an i64 or UUID (never contains `:`), and file keys are storage-backend paths that don't idiomatically contain `:` either — so this isn't an active exploit path. But the design doc's "no caller-in-key footgun" / "collision-free" framing (§5 of the design spec) isn't airtight as written: it holds only because of an unstated assumption about both components' charsets. Recommended fix (when picked up): length-prefix each component (`format!("mediaacc:{}:{key}:{}:{caller_id}", key.len(), caller_id.len())`) or hash the pair into a single opaque token, either of which makes the key injective regardless of content. Scope: `plugins/umbral-storage/src/lib.rs` (`media_access_cached`'s `cache_key` construction), plus a regression test once a non-i64/UUID `Identity::user_id()` or colon-bearing file-key scheme is a real target.
