7. [x] **Materialized models / computed fields should auto-refresh when their source tables change** — SHIPPED (2026-09-24, v1). A column on model `M` can be declared *materialized* — the framework recomputes it and writes it back automatically whenever a declared source table changes, so the dependency is expressed at exactly one site and never goes silently stale.

    **Surface (builder registration, no derive change — the column stays an ordinary typed field):**
    `App::builder().materialize(Materialized::<M>::field(col).from::<S>(|s| Some(key)).recompute_typed(|pk| async move { ... }))`. `.field(col)` names the target column (any column token via `AsRef<str>`); `.from::<S>(key_fn)` registers a source model `S` + `Fn(&S) -> Option<Pk>` mapping a changed source row to the affected target pk (`None` skips; multiple sources allowed, all sharing the recompute); `.recompute_typed(f)` returns the fresh value, which the framework writes back. The generics are erased into a non-generic `MaterializedSpec` (`SourceReg` + `Arc<dyn Fn>` closures over `serde_json::Value` at the boundary), so `AppBuilder` holds a `Vec<MaterializedSpec>`.

    **Mechanism (eager, after-commit; `crates/umbral-core/src/orm/materialized.rs`):** at `build()` each spec is validated (target column exists, model has a single-column pk, target ≠ pk — a bad spec aborts boot via `BuildError::Materialized`) and then `install`ed: an **async** handler (`signals::subscribe_async`, reusing gaps6 #15's after-commit delivery — NOT `subscribe_txn`, which would deadlock SQLite's single writer and couple the source-write latency) is subscribed to `post_save:<S>` and `post_delete:<S>` for each source. Write-back errors are logged, never propagated (a committed source write can't be failed by an after-commit handler).

12. [x] **`media_access_cached` has a cache miss-compute/bust write-skew race** — SHIPPED (2026-09-24). A revocation's `bust_tag` landing between a media-access cache miss and its store no longer loses to the stale, just-computed `allow` (which previously survived until TTL, default 60s).

    **Fix — a guarded store (the "store-time re-check against the bust log" this entry named), kept backend-agnostic in the `Cache` handle.** The core `umbral::cache::TaggedCache` contract (`crates/umbral-core/src/cache.rs`) gained two methods with backward-compatible default impls: `bust_epoch() -> u64` (a monotonic counter that advances on every bust) and `set_tagged_bool_guarded(key, value, ttl, tags, since_epoch) -> bool` (store UNLESS one of `tags` was busted after `since_epoch`). `media_access_cached` (`plugins/umbral-storage/src/lib.rs`) now captures `cache.bust_epoch()` **before** running the developer's closure and stores through the guarded variant.

    **Mechanism (`plugins/umbral-cache/src/lib.rs`):** a process-wide `BustLog` (an `AtomicU64` counter + a `Mutex<HashMap<tag, last_bust_epoch>>`), shared across every clone of a `Cache` via `Arc`. Both bust paths (`Cache::bust_tag` and the `TaggedCache::bust_tag` impl) call `BustLog::record` — which bumps the counter and stamps the tag's epoch **before** the backend evicts the tag's keys. `set_tagged_bool_guarded` does a **pre-check** (skip the store outright if already stale) and, after storing, a **post-check** that compensates for a bust racing the store itself: because the epoch is stamped before eviction, any bust whose eviction could have missed the not-yet-written value is visible to the post-check, which then deletes it — so either the racing bust's own eviction removed the value or the post-check does. The guard is **per-tag** (an unrelated tag's bust doesn't force a recompute) and lives above the `CacheBackend` trait, so memory / SQLite / Redis are all covered without per-backend changes; the failure mode stays "recompute," never "serve-stale."

    **Tests (TDD, `plugins/umbral-cache/tests/tagged_write_skew.rs`):** `a_bust_between_epoch_capture_and_store_defeats_the_stale_allow` (RED before the fix — the stale allow was cached; replays the exact epoch-capture → bust → guarded-store sequence `media_access_cached` performs), `a_clean_compute_is_cached_and_still_bustable` (guard doesn't break ordinary caching or later invalidation), `a_bust_of_an_unrelated_tag_does_not_block_the_store` (per-tag precision). [ ] **`FieldSpec::max_length` emits a hard `varchar(N)` but is validated by NO write path — an over-long value reaches Postgres and surfaces as a 500, not a 400** — found in production on TaskFlow v2 (2026-09-27). Pasting a 12,617-character markdown file into a task description (`varchar(12000)`) made `POST /api/taskflow_task/` return a 500. Postgres logged `ERROR: value too long for type character varying(12000)` against the generated `INSERT INTO "taskflow_task" (...)`. The request was 617 characters over a limit the framework itself had declared.

    **The gap.** `#[umbral(string, max_length = N)]` is stored as `FieldSpec::max_length` (`crates/umbral-core/src/orm/model.rs`, ~line 654) — and its own doc-comment describes it as *"Soft length cap for display… The admin truncates the value at this many characters when rendering it in `list_display`."* The migration engine nevertheless **reads it to emit `varchar(N)`**, which is a hard constraint. It is then enforced by nobody: `validate_on_create` (`crates/umbral-core/src/orm/validation.rs:47`) runs required / choices / M2M / FK only, `WriteError` (`crates/umbral-core/src/orm/write.rs:48`) has no length variant, and the dynamic insert seam `build_insert_plan` (`crates/umbral-core/src/orm/dynamic.rs:4065`) checks `validate_numeric_bounds` and `validate_text_format` but never the length. So the attribute is documented as decoration, compiled as a constraint, and validated as neither.

    **Why it becomes a 500 rather than a 400.** The value is bound and sent; Postgres raises SQLSTATE 22001; sqlx surfaces it as a decode/database error. `From<sqlx::Error> for ApiError` (`plugins/umbral-rest/src/lib.rs:2567`) special-cases only `sqlx::Error::Protocol` → generic 400, so everything else lands on `ApiError::Sqlx` → the 500 arm (`lib.rs:~2701`), which deliberately hides DB text from the client (WEB-5). The caller therefore gets an opaque "internal server error" for a mistake the request body itself made, with no field name and no limit.

    **The inconsistency that makes this a bug rather than a policy.** The *same attribute name* is enforced for DTOs: `#[derive(Validate)]` + `#[umbral(max_length = N)]` → `umbral_core::validate::check_max_length` (`crates/umbral-core/src/validate.rs:161`) rejects with `"Must be at most {n} characters (got {len})."`. So `max_length` means "enforced, with a good message" on a DTO and "display hint" on a model, and a model write accepts values its own DDL rejects. `validate.rs`'s own module doc states the principle being violated: *"A string a DTO accepts is a string the model accepts."*

    **Why it is invisible until production.** SQLite does not enforce `varchar(N)` — it is a type affinity, not a constraint. Local dev and the whole test suite run on SQLite (`umbral-testing::boot` → `sqlite::memory:`), so an over-long value inserts happily there and only fails on Postgres. A regression test cannot reproduce the 500 on the test harness; it must assert the **pre-DB rejection** (error variant + field key), which holds on both backends.

    **Evidence of demand: two apps have already hand-rolled this.** TaskFlow added `plugins/taskflow-design/src/validation.rs:68 MAX_FILE_BYTES = 128 * 1024` to guard `DesignFile::content` (`varchar(262144)`) at the write path, and a second app-level cleaner registered over `FieldSpec::max_length` via `umbral::cleaners::register_cleaner` for every capped field (the workaround that prompted this entry). Both exist only because the ORM does not do it, and both are one-sided — see #23 for why the cleaner half is incomplete.

    **Recommended fix.** Enforce it in the ORM's pre-DB validation, so every surface inherits it exactly as the module doc already promises ("centralising them here means the admin plugin and any third-party caller get the same structured errors"). Add `validate_text_lengths(meta, body)` to `crates/umbral-core/src/orm/validation.rs` and call it from all five validators — `validate_on_create`, `validate_on_create_in_tx`, `validate_on_typed_create`, `validate_on_update`, `validate_on_update_in_tx` — so the rule also covers nested and bulk creates rather than just single REST writes. Emit `WriteError::Validator { field, message }` reusing `check_max_length`'s exact wording (`"Must be at most {n} characters (got {len})."`), which umbral-rest already renders as a 400 with a per-field map and `code: "validator_failed"` — zero changes needed in `umbral-rest`. Optional refinement: a dedicated `WriteError::MaxLengthExceeded { field, limit, actual }` carrying the numbers structurally, so a client can render a counter without parsing prose; it costs four match arms (`Display`, `is_validation`, `field_errors`, `code`).

    **Two details to get right.** (a) Count **characters, not bytes** — `varchar(N)` counts characters, and `str::len()` would reject legal accented text; `chars().count()` matches Postgres and matches `check_max_length`'s existing behaviour. (b) Run the check on the **post-normalisation** value, i.e. after `trim`/`lowercase` at the seam, because the trimmed value is what the database actually receives. (c) Rectify the `FieldSpec::max_length` doc-comment, which currently tells developers it is display-only — that sentence is what makes this look intentional.

    **Scope:** `crates/umbral-core/src/orm/validation.rs` (the new check + five call sites), `crates/umbral-core/src/orm/model.rs` (doc-comment), optionally `crates/umbral-core/src/orm/write.rs` (a structured variant). No `umbral-rest` change required if `Validator` is reused. Update `documentation/docs/v0.0.1/orm/` to state that `max_length` is enforced pre-DB.

    **Tests:** `crates/umbral-core/tests/declared_lengths.rs` — over-cap is rejected before the DB with the field key and a message naming limit + actual; exactly-at-cap is accepted; one-over is rejected; each field is held to its **own** cap (so a single global constant cannot pass by accident); a non-string value on a capped column is left to `json_to_sea_value`; a `max_length = 0` field is skipped. Integration proof on Postgres (`crates/umbral-core/tests/`, pg-gated) that the previously-500ing request now returns 400 — the SQLite suite structurally cannot assert this one.

    **App-side workaround to delete when this lands:** TaskFlow's `backend/src/validation.rs` (+ its `install()` call in `main.rs`) and `plugins/taskflow-design/src/validation.rs::MAX_FILE_BYTES`.

Every other seam has one: `write_helpers.rs:136` (typed single insert), `write_helpers.rs:225` (typed bulk_create), `dynamic.rs:2323`, `dynamic.rs:2551` and `dynamic.rs:4124` (the dynamic insert/update paths plus the shared `build_insert_plan`).     **Recommended fix.** One `cleaners::apply` call in `build_update_for`'s column loop, placed **after** `normalize_json` and **before** `json_to_sea_value` — the same ordering as the other four seams, so a hook always sees the normalised value. A RED-first assertion is easy here: today the update succeeds and the bad value lands.

    **Scope:** `crates/umbral-core/src/orm/queryset/mod.rs` (one call site + ordering comment), `crates/umbral-core/tests/field_cleaners.rs`. If #22 lands first, the length rule can be shared between both seams rather than duplicated.
