# gaps6

1. [ ] **Field-name → `&str` from the model, typo-safe + autocompleted** — the user hand-types column-name string literals (`"username"`) in many places (`select_related`, `values`, `order_by`, `search_fields`, ad-hoc lookups), which is error-prone. Ask: `AuthUser::USERNAME` should yield the `&'static str` `"username"` so a mistyped field is a compile error and the editor autocompletes it.

    **Constraint:** `Model::USERNAME` is *already* taken — `#[derive(Model)]` emits it as a typed **column token** (`pub const USERNAME: <Col>Col<Model>`, see `crates/umbral-macros/src/lib.rs:272`) used for `.eq()` / `.to()` / `.order_by()`. It cannot simultaneously *be* a bare `&str` (associated-const name collision). So the design is to expose the name **off the existing token**, not to redefine `Model::USERNAME`.

    **Recommended design:** give the column token a `pub const fn name(&self) -> &'static str` **and** an `AsRef<str>` / `Display` impl, so `User::USERNAME.name()` returns `"username"` and the token can be passed anywhere a `&str` / `impl Into<String>` column name is accepted (e.g. `select_related`, `values(&[...])`). This preserves autocomplete (you type `User::` and see every field) and makes a typo a compile error. Alternative if a bare-const form is wanted: a sibling lowercase module already exists (`user::NAME`, `session::ID` are also typed column tokens) — do NOT add a colliding string const there; prefer the `.name()` method on the one token type.

    **Scope:** `crates/umbral-macros/src/lib.rs` (emit `name()` / `AsRef<str>` on the generated `Col` type — likely once on the generic `Col<M>` in `umbral-core`, not per field), `crates/umbral-core/src/orm/` (the `Col` type), a re-export check in the facade, one behavioral test (`User::USERNAME.name() == "username"` and a `select_related`/`values` call driven by the token), and a short `documentation/docs/v0.0.1/orm/` note. Small, self-contained; **orthogonal to the ORM heavy-relations epic** (`docs/specs/orm-heavy-relations-epic.md`) — that epic is the relation→JOIN engine, this is scalar field-name metadata. Can be picked up independently.

2. [ ] **IDOR object-scope check: cover auto-exposed models, not just explicit `ResourceConfig`s** — follow-up to gaps5 #101 / tf#322 (the `security.object_scope` boot check, shipped). Today the REST check (`plugins/umbral-rest/src/lib.rs` `system_checks`) walks only tables that had an explicit `ResourceConfig` (`configured_resources`), faithful to the design spec's wording "for every registered `ResourceConfig`". But umbral auto-exposes **every** registered model at `/api/<table>/` with full CRUD by default (opt-out, see `rest/exposure.mdx`). So a writable model with **no** explicit `.resource(...)` call — precisely the "forgot to scope it" case the check exists to catch — is never flagged. The check currently misses the largest slice of the IDOR surface.

    **Constraint:** the REST plugin can't cheaply enumerate the auto-exposed set at `system_checks()` time. `system_checks(&self)` sees `&self` but not the model registry, and the exposure decision (the internal framework-table blocklist + `include_only` / `exclude` + `hide`) is applied at route-build time. That decision must be shared with, or reproduced inside, the check.

    **Recommended design:** at check time, walk the registered models (the same source route-build uses), apply the exposure rules, and treat an auto-exposed writable table exactly like a configured one: `write_enabled && !object_scoped && !acked` → a `security.object_scope` finding. Reuse the existing `resource_write_enabled` / `resource_object_scoped` / `unscoped_acks` helpers unchanged — the only new part is computing the auto-exposed writable table set. The table-keyed ack markers (`rls_backed()` / `unscoped_ok(..)`) already apply to any table, so they silence auto-exposed findings too.

    **Scope:** `plugins/umbral-rest/src/lib.rs` (extend `system_checks` to include the auto-exposed writable set — likely needs the model list threaded to the check, the way `CheckContext` already carries `registered_plugin_names`; may want a small core assist so the plugin need not re-derive the model registry), behavioral tests (an auto-exposed model with no `.resource()` and no scope warns; `owned_by` / `rls_backed` / `unscoped_ok` / hiding writes clears it), and a one-line note in `documentation/docs/v0.0.1/security/object-level-authorization.mdx`. Deferred from #322 as a spec-scoped v1 boundary (RLS auto-detect was option B2, also deferred); this closes the gap to the real default write surface. TaskFlow task filed alongside this entry.

3. [ ] **`filter_annotation()` + `first()`/`exists()`/`get()` loses the SQL `LIMIT` optimization** — after the heavy-relations aggregates work (commit f91c7544), `build_query_for`'s annotation-filter wrap does `q.reset_limit()/reset_offset()` and re-applies only the *tracked* `user_limit`/`user_offset` to the outer statement. But `QuerySet::first()`/`first_pg()` and `tx::QuerySetTx::first()/exists()/get()` set `self.query.limit(n)` **directly** (bypassing the tracked builder), so when chained after `.filter_annotation(...)` that inner `LIMIT 1`/`LIMIT 2` is stripped and never restored — the terminal fetches the ENTIRE filtered row set and picks the first in Rust. **Correctness is intact** (arguably more correct than before), but it's a latency regression against the epic's own least-latent-shape principle on this specific combo, and it's untested. Fix: have those direct-`self.query.limit()` terminals route through the tracked `user_limit` path (so the outer-wrap re-applies it), or have the wrap also preserve a directly-set inner limit. Scope: `crates/umbral-core/src/orm/queryset/mod.rs` (`first`/`first_pg` ~2335/4393), `queryset/tx.rs` (~77/138/166), + a test `filter_annotation().first()` issues `LIMIT 1` over the filtered set. Low priority (uncommon combo, correctness-safe).

4. [ ] **`resolve_join_hops`/`resolve_m2m_chain` decode-path duplicates `RelPath::from_path` resolution** — after the walk_joins JOIN-builder convergence (TaskFlow #445, commit c9b8426c), JOIN *emission* is unified through `walk_joins`, but path *table resolution* still exists twice: `RelPath::from_path` (used to BUILD the JOINs) and the shrunk `resolve_join_hops`/`resolve_m2m_chain` (kept, `JoinHop` down to just `child_table`, to resolve hop tables for `backend_sqlite`/`backend_pg` post-fetch column decode). If the two ever disagree on a path's tables, `apply_join_related` would JOIN one shape and hydration decode another. Low risk today (both tested, agree on supported shapes), documented. Fix: have the decode path read `hop.to_table` off `RelPath::from_path` instead of the parallel resolver, retiring `resolve_join_hops`/`resolve_m2m_chain` entirely. Scope: `crates/umbral-core/src/orm/queryset/{mod.rs,backend_sqlite.rs,backend_pg.rs}`. Low priority (latent, no current divergence).

5. [ ] **Deep-path aggregates soft-delete-scope the LEAF only, not intermediate hops** — `build_aggregate_subquery` (crates/umbral-core/src/orm/queryset/aggregate_path.rs, ~:653-665, documented there) excludes soft-deleted LEAF rows for a soft-delete model, matching the single-hop path, but does NOT apply `deleted_at IS NULL` to intermediate hop tables in a deep path (e.g. `annotate_count("posts__comments")` where `posts` is soft-deletable counts comments under a soft-deleted post). Affects aggregate COUNTS over soft-deleted intermediates — NOT exposure of hidden column values. Documented as a deliberate v1 boundary; keep tracked. Fix: thread per-hop soft-delete predicates through `walk_joins` for the aggregate subquery. Low priority.
