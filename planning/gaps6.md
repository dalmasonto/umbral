7. [x] **Materialized models / computed fields should auto-refresh when their source tables change** — SHIPPED (2026-09-24, v1). A column on model `M` can be declared *materialized* — the framework recomputes it and writes it back automatically whenever a declared source table changes, so the dependency is expressed at exactly one site and never goes silently stale.

    **Surface (builder registration, no derive change — the column stays an ordinary typed field):**
    `App::builder().materialize(Materialized::<M>::field(col).from::<S>(|s| Some(key)).recompute_typed(|pk| async move { ... }))`. `.field(col)` names the target column (any column token via `AsRef<str>`); `.from::<S>(key_fn)` registers a source model `S` + `Fn(&S) -> Option<Pk>` mapping a changed source row to the affected target pk (`None` skips; multiple sources allowed, all sharing the recompute); `.recompute_typed(f)` returns the fresh value, which the framework writes back. The generics are erased into a non-generic `MaterializedSpec` (`SourceReg` + `Arc<dyn Fn>` closures over `serde_json::Value` at the boundary), so `AppBuilder` holds a `Vec<MaterializedSpec>`.

    **Mechanism (eager, after-commit; `crates/umbral-core/src/orm/materialized.rs`):** at `build()` each spec is validated (target column exists, model has a single-column pk, target ≠ pk — a bad spec aborts boot via `BuildError::Materialized`) and then `install`ed: an **async** handler (`signals::subscribe_async`, reusing gaps6 #15's after-commit delivery — NOT `subscribe_txn`, which would deadlock SQLite's single writer and couple the source-write latency) is subscribed to `post_save:<S>` and `post_delete:<S>` for each source. On a source event it decodes `payload["instance"]` → `key_fn` → affected pk → `recompute(pk)` → writes back through the ORM (`DynQuerySet::filter_pk_eq(&pk).update_json({col: value})` — a new generic-pk filter that coerces i64/String/Uuid pks and matches nothing on a bad/absent pk). The recompute+write-back is wrapped in a task-local re-entrancy guard (`guarded`) that skips a same-`(table,col)` self-cascade with a warning while allowing nested different-key cascades and never blocking independent concurrent tasks. Write-back errors are logged, never propagated (a committed source write can't be failed by an after-commit handler).

    **Tests (behavioral, real rows, public ORM path):** `crates/umbral-core/tests/materialized_fields.rs` (create/update/delete auto-refresh with zero manual recompute; a rolled-back source tx fires no refresh — after-commit proof; a `key_fn`→`None` row triggers no write-back), `crates/umbral-core/tests/materialized_fields_str_pk.rs` (String-pk target, proving the write-back isn't i64-hardcoded), `crates/umbral-core/tests/materialized_validation.rs` (a misdeclared field aborts boot), plus in-crate unit tests for the erasure and the guard. Doc: `documentation/docs/v0.0.1/orm/materialized-fields.mdx`. Design + plan: `docs/superpowers/specs/2026-09-24-materialized-computed-fields-design.md`, `docs/superpowers/plans/2026-09-24-materialized-computed-fields.md`.

    **Deferred to later entries:** cached-aggregate / `annotate_*` integration with the heavy-relations epic; deferred (task-queue) refresh; partial/incremental recompute; cross-materialized-field dependency graph + full cycle detection (v1 catches direct self-cascade only).

12. [x] **`media_access_cached` has a cache miss-compute/bust write-skew race** — SHIPPED (2026-09-24). A revocation's `bust_tag` landing between a media-access cache miss and its store no longer loses to the stale, just-computed `allow` (which previously survived until TTL, default 60s).

    **Fix — a guarded store (the "store-time re-check against the bust log" this entry named), kept backend-agnostic in the `Cache` handle.** The core `umbral::cache::TaggedCache` contract (`crates/umbral-core/src/cache.rs`) gained two methods with backward-compatible default impls: `bust_epoch() -> u64` (a monotonic counter that advances on every bust) and `set_tagged_bool_guarded(key, value, ttl, tags, since_epoch) -> bool` (store UNLESS one of `tags` was busted after `since_epoch`). `media_access_cached` (`plugins/umbral-storage/src/lib.rs`) now captures `cache.bust_epoch()` **before** running the developer's closure and stores through the guarded variant.

    **Mechanism (`plugins/umbral-cache/src/lib.rs`):** a process-wide `BustLog` (an `AtomicU64` counter + a `Mutex<HashMap<tag, last_bust_epoch>>`), shared across every clone of a `Cache` via `Arc`. Both bust paths (`Cache::bust_tag` and the `TaggedCache::bust_tag` impl) call `BustLog::record` — which bumps the counter and stamps the tag's epoch **before** the backend evicts the tag's keys. `set_tagged_bool_guarded` does a **pre-check** (skip the store outright if already stale) and, after storing, a **post-check** that compensates for a bust racing the store itself: because the epoch is stamped before eviction, any bust whose eviction could have missed the not-yet-written value is visible to the post-check, which then deletes it — so either the racing bust's own eviction removed the value or the post-check does. The guard is **per-tag** (an unrelated tag's bust doesn't force a recompute) and lives above the `CacheBackend` trait, so memory / SQLite / Redis are all covered without per-backend changes; the failure mode stays "recompute," never "serve-stale."

    **Tests (TDD, `plugins/umbral-cache/tests/tagged_write_skew.rs`):** `a_bust_between_epoch_capture_and_store_defeats_the_stale_allow` (RED before the fix — the stale allow was cached; replays the exact epoch-capture → bust → guarded-store sequence `media_access_cached` performs), `a_clean_compute_is_cached_and_still_bustable` (guard doesn't break ordinary caching or later invalidation), `a_bust_of_an_unrelated_tag_does_not_block_the_store` (per-tag precision). Full `umbral-cache` + `umbral-storage` suites green; redis-feature build clean; clippy clean. Doc: `documentation/docs/v0.0.1/cache/tagged-invalidation.mdx` ("The bust-during-compute race").

[x] **The whole `on_tx()` write path is signal-free — deployed apps silently miss signals on transactional writes** — SHIPPED (2026-09-20, branch `feat/tx-after-commit-signals`). `crates/umbral-core/src/orm/queryset/tx.rs`'s `create`, `update_values`, `delete` (both hard-delete and the soft-delete-in-tx branch) now buffer the SAME signals their non-tx counterparts emit (`post_save`, per-row `post_delete` incl. #14's has-subscribers-gated full-row payload, `bulk_post_save`, `bulk_post_delete`), and the buffer is flushed only after the enclosing transaction commits — never on rollback.

    **Mechanism (after-commit delivery, not mid-transaction emit — the naive fix this entry explicitly ruled out):** `crates/umbral-core/src/db.rs`'s `Transaction` struct gained a `pending_signals: Vec<PendingSignal>` field, where `PendingSignal = Box<dyn FnOnce() -> Pin<Box<dyn Future<Output = ()> + Send>> + Send>` — a boxed emit closure, not a `(name, payload)` pair, so the buffered work calls the exact same `crate::signals::emit_*_by_table` helpers the non-tx path uses (zero re-derived payload shaping or redaction). `Transaction::push_pending_signal` (called by `tx.rs` write terminals) and `Transaction::take_pending_signals` (called by the runners) are `pub(crate)`. All four transaction runners (`transaction`, `transaction_on`, `transaction_sqlite`, `transaction_pg`) now do: on `Ok`, drain the buffer with `take_pending_signals()` **before** `commit()`, call `commit()`, then run each drained closure; on `Err`, `rollback()` as before — the buffer is never drained, so it drops with the `Transaction` and nothing fires. `serialize_for_signal` (the single redaction choke point behind `emit_post_save`/`emit_post_delete`, strips `SIGNAL_SKIP_FIELDS`) was widened from private to `pub(crate)` so `tx.rs` can call it directly instead of re-implementing redaction.

    `QuerySetTx::create()` buffers `post_save` (created=true) via `serialize_for_signal` + `emit_post_save_by_table`. `QuerySetTx::update_values()` now adds a `RETURNING <pk>` clause (it previously used a plain `execute()` with no ids) and buffers `bulk_post_save` with the matched ids. `QuerySetTx::delete()` mirrors the non-tx `QuerySet::delete()` exactly: `has_subscribers("post_delete:<table>")` gates `RETURNING *` (full row, per-row payload) vs `RETURNING <pk>` (pk-only payload); every full-row payload has `T::SIGNAL_SKIP_FIELDS` stripped before buffering; both branches also buffer one `bulk_post_delete`. The soft-delete-in-tx branch (`soft_delete_in_tx`) now also `RETURNING`s the pk and buffers `bulk_post_delete` only, matching the non-tx `soft_delete_update`'s bulk-only contract.

    **Tests (TDD, `crates/umbral-core/tests/tx_after_commit_signals.rs`, all against `db::transaction_sqlite`):** `tx_create_fires_post_save_after_commit` (fires exactly once, and the row is already readable by an independent query by the time the subscriber runs — proves after-commit, not just after-return); `tx_create_fires_nothing_on_rollback` (the crux test — a `create()` followed by an `Err` return fires ZERO signals and the row genuinely doesn't exist; this was RED before the fix only in the sense that a naive inline-emit implementation would have made it fail — the actual pre-fix code already fired nothing at all, so the meaningful RED→GREEN transition is on the commit-path tests, not this one); `tx_delete_fires_post_delete_after_commit_not_on_rollback` (delete variant of both); `tx_update_values_fires_bulk_post_save_after_commit`; `tx_writes_redact_signal_skip_fields` (a `#[umbral(signal_skip)]` field is absent from both the tx create and tx delete payloads). Full `cargo test -p umbral-core` suite green, `cargo clippy -p umbral-core --all-targets` clean.

    **Boundary documented, not fixed (by design):** a transaction opened via a raw `db::begin()`/`begin_sqlite()`/`begin_pg()` and committed by the caller directly (not through `db::transaction*`) has no umbral-owned commit to hook — signals buffered on it are silently dropped when the `Transaction` value is dropped. This is safe (never a phantom signal) but silent, so it's called out in `documentation/docs/v0.0.1/plugins/signals.mdx` under a new "Transactional writes (`on_tx`)" section: use `db::transaction(...)` (or its `_on`/`_sqlite`/`_pg` siblings) whenever signals need to fire.

    Ties into **gaps5 #52** (transactional outbox / after-commit integration) and **gaps5 #57** (in-process signals note) — this closes the near-term, deployed-impact half of that story for the ORM's own signal registry; a durable cross-process outbox is still open ground for #52.

16. [x] **`on_tx()` writes skip the audit-log (`audit_pre`/`audit_post`), unlike the non-tx path** — SHIPPED (2026-09-24). An `#[umbral(audited)]` model mutated inside `on_tx()` (create / update_values / delete / soft-delete) now records to `umbral_audit`, matching the non-tx path (gaps3 #54).

    **Why it's not "call the same helper":** the non-tx `audit_pre`/`audit_post` (`crates/umbral-core/src/orm/queryset/mod.rs`) read the pre/after image and write the audit row through the **ambient pool** (`audit::record` → `DynQuerySet::insert_json`). Reusing them from a `QuerySetTx` would (a) **deadlock on SQLite** — only one writer may hold the database, so an ambient-pool INSERT into `umbral_audit` while the caller's write tx is still open blocks on that open writer and times out — and (b) record a **stale after-image** for UPDATE/CREATE, because a separate connection can't see the tx's own uncommitted write. So the audit read AND write are threaded through the SAME transaction, which also makes the audit row **roll back with the business write** (no audit trail for a change that never happened).

    **Mechanism:** two tx-bound helpers on `QuerySetTx` (`crates/umbral-core/src/orm/queryset/tx.rs`) — `audit_pre_in_tx` (pre-image) and `audit_post_in_tx` (after-image re-read BY PK for CREATE/UPDATE, empty for DELETE; then diff + record) — mirror `QuerySet::audit_pre`/`audit_post` but route through the tx. They stand on: `orm::dynamic::audit_snapshot_in_tx` + a new multi-row `DynQuerySet::fetch_all_json_in_tx` (the multi-row sibling of `fetch_one_json_in_tx`, reading through the tx connection); and `orm::audit::record_in_tx`/`record_many_in_tx` (write the audit row via `DynQuerySet::insert_json_in_tx`). `record`/`record_in_tx` share a new `audit_body` builder so the ambient and tx paths can't drift on the row shape. `create()` records CREATE directly with its serialized RETURNING row (before=None), mirroring the non-tx single-create; `update_values()` gained the audit_pre/post pair; `delete()` and `soft_delete_in_tx()` audit as DELETE (soft delete logs as delete). Every audit call runs while the tx is open (before the after-commit signal buffer), so it commits/rolls back atomically.

    **Tests (TDD, `crates/umbral-core/tests/tx_audit_trail.rs`, all against `db::transaction_sqlite`):** `tx_create_update_delete_are_all_audited_after_commit` (RED before fix: tx path wrote zero audit rows; also asserts the UPDATE after-image is `to = 250`, guarding against a stale ambient-pool read), `a_rolled_back_tx_writes_no_audit_rows` (the audit row is transactional), `a_tx_soft_delete_is_audited_as_delete`. Full `cargo test -p umbral-core` green; `cargo clippy -p umbral-core --lib` clean for the touched files.
