36. **`GroupPolicy` is synchronous, so realtime rooms can't be gated on async state (DB membership).** `GroupPolicy::can_join(&self, user_id: Option<&str>, group: &str) -> bool` (and `can_send`) is a sync fn with no async variant. A realtime app that wants to admit a user to `project:{id}:*` only if they hold an active membership row must run a DB query at the SSE/WS handshake — which cannot be `.await`ed inside a sync `can_join`. This matters for confidentiality, not just metadata: with field-projected exposures (e.g. a chat message exposing `body_markdown`), a non-member who joins the group receives real row content over SSE, and REST-side scoping does not cover the realtime path. Current downstream workaround (local_task_tracker SP-A): `tokio::task::block_in_place` + `Handle::current().block_on(...)` inside `can_join` — correct only on a multi-thread runtime (panics on current-thread) and blocks one worker thread per room-join for the duration of the membership query. **Proposed fix:** add an async policy hook to `RealtimePlugin` — e.g. an `AsyncGroupPolicy` trait with `async fn can_join(&self, identity: Option<&Identity>, group: &str) -> bool` (and `can_send`), resolved at the handshake alongside the existing async `identity_resolver`; keep the sync `GroupPolicy` for shape-only checks. Downstream can then drop the `block_in_place` bridge. Ship with a test that a non-member is refused a private group at the SSE handshake while a member is admitted, and that the handshake does not block a worker thread. (local_task_tracker phase2 SP-A)

**SHIPPED** (commit `76699a6a`). 37. **`ResourceConfig::scope_async` governs reads but NOT creates — a caller can POST a row into a project scope they cannot read.** `scope`/`scope_async` restrict list/retrieve/update/delete to the caller's in-scope rows (audit_2 H1/P2), but `Create` is not constrained by the scope decision at all: the `ScopeDecision` (`Restrict` / `RestrictIn` / `None`) is applied to the query the built-in list/detail/update/destroy handlers build, and the create handler never consults it. So on a membership-scoped resource — `scope_async(|id| RestrictIn("project", my_active_project_ids))` — an authenticated caller who is NOT a member of project P can still `POST /api/<table>/ { "project": P, ... }` and inject a row into P's scope, even though every read of that scope returns nothing to them. When the scoped column is *also* access-granting (e.g. a `project_member` row whose existence the read-scope then honours), this is a privilege escalation, not merely a write-IDOR: the create bootstraps the read access. Downstream (local_task_tracker SP-A hardening) had to work around this by locking the access-granting tables to `.views([List, Retrieve])` — a coarse "no client writes at all", which is right for server-managed tables but does not help a table the app legitimately writes from the client (a non-member can still POST a task/message into a foreign project — a residual write-injection IDOR). The existing narrower hooks don't cover it: `owner_field` injects the *caller's identity* into an owner column (not a membership check against an arbitrary FK), and `under(parent, fk)` injects the parent id from the URL (nested routes only). **Proposed fix:** make `Create` honor the same `ScopeDecision` — reject (404/403, no oracle) a create whose scoped column value falls outside the caller's scope, i.e. for `RestrictIn(col, allowed)` require the body's `col` ∈ `allowed`, for `Restrict(pairs)` require each `(col,val)` to match, and for `None` reject outright. This closes the create-into-foreign-scope hole generically wherever a resource already declares a read scope, with no per-app workaround. Ship with a test: a caller scoped to project P is refused a `POST { project: Q }` (Q out of scope) while `POST { project: P }` succeeds. (local_task_tracker phase2 SP-A hardening)

**SHIPPED** (commits `432d5c14` rest + `ae76b2d8` orm, exactly the proposed shape). `object_scope_allows_create` — the write-side twin of `object_scope_hook` — checks the body's scoped column against the raw `ScopeDecision`: `RestrictIn(col, allowed)` requires body `col` ∈ `allowed` (normalized through the same `typed_restrict_in_values` the read filter binds with, so `1` vs `"1"` can't diverge), `Restrict(pairs)` requires each pair to match, `None` refuses every create, absent scoped column = deny. Every denial is the same 404 regardless of whether the target exists, is foreign, or is absent — no oracle. Runs AFTER `inject_owner_field`/`inject_parent` so server-injected values participate; wired into the single create, per-item in `bulk_create`, and per-child in `insert_nested_tree` (after FK injection). Same class, also closed: `bulk_update`/`bulk_delete` updated/deleted by bare PK with no scope condition — they now AND the read-side scope like their single-object twins. That fix surfaced a real ORM bug: `update_json_in_tx` returned `parent_pks.len().max(1)` (a zero-row UPDATE claimed "1 affected", so a bulk update of a nonexistent/out-of-scope pk answered 200) — fixed to return the real `rows_affected()`. Tests in `membership_scope.rs` (member create 201, foreign create 404 byte-identical to nonexistent-club 404, empty-scope/anonymous/missing-column denied, bulk PATCH out-of-scope = "no row", bulk DELETE skips out-of-scope) + `dyn_queryset_tx.rs::update_json_in_tx_reports_zero_for_a_no_match_where`. Docs: rest/permissions.mdx scoping section.

38. **The realtime plugin sends data in a sequentially ie from the first user to the next to the next. This is like 0(N) instead of 0(1) - Is it possible to use something like Rayon for the same?**

**SHIPPED** (commit `323a0f9c`) — with a finding: Rayon is the wrong tool. The dispatch loop was already non-blocking (`try_send`, no await, no lock held; `tests/scale.rs` pins a 10k broadcast in single-digit ms), so the O(N) cost was CPU, not I/O waits: each subscriber got `event.clone()` — a deep recursive clone of the JSON payload — and each transport then re-serialized the same JSON to text once per connection. The per-connection channels now carry `Arc<Delivery>`: ONE allocation per dispatch, a refcount bump per subscriber, and `Delivery` lazily renders each transport's wire frame (SSE envelope / WS text frame) once into a shared `OnceLock` cache — the first recipient serializes, everyone else memcpys the finished string. `Delivery` derefs to `Event` (private inner field — a public `event: Event` would shadow `Event::event` through the deref). Test: `dispatch_shares_one_delivery_across_subscribers` pins Arc-identity across subscribers and pointer-identity of the rendered frame.

39. **Filtering a `#[umbral(choices)]` field takes a raw string, not the `Choices` variant — the typed field constant loses the enum.** Every filter on a choices-backed column in the codebase passes a string literal: `product::STATUS.eq("active")`, `post::STATUS.eq("published")`, `ful_job::STATUS.eq("pending")` — there are zero `.eq(SomeEnum::Variant)` uses anywhere. So even though `status` is declared as a strongly-typed `Choices` enum on the model, and the field handle `task::STATUS` is a typed column, `.eq()` accepts an arbitrary `&str`. A typo (`"in_progres"`, `"done "`, a value that doesn't match `#[choices(rename_all = ...)]`) compiles fine and silently matches no rows. This directly contradicts the framework's stated value prop — CLAUDE.md lists "stringly typed filters where a typed filter is available" among the boring mistakes the ORM is supposed to prevent, and the whole "declare the enum once, every surface honours it" story leaks here: the write path and admin dropdown are enum-typed, but the query path is not. **Proposed fix:** for a field declared `#[umbral(choices)]` over an enum `E: Choices`, generate the column handle so `.eq(E)` / `.ne(E)` / `.in_([E])` accept the variant and serialize it through the *same* `Choices` mapping used at write time (so `#[choices(rename_all = "snake_case")]` stays single-sourced) — `task::STATUS.eq(TaskStatus::InProgress)` renders `status = 'in_progress'`. Keep a string-accepting form for dynamic/late-bound callers (`DynQuerySet`, admin filters, query-param parsing) where the enum type isn't statically known. Net effect: a bad status becomes a compile error, and the rename mapping can never drift between the write and read paths. Ship with a test: `Task::objects().filter(task::STATUS.eq(TaskStatus::InProgress))` returns the in-progress rows and the generated SQL binds `'in_progress'`, and a round-trip create+filter reads the row back. (surfaced writing the "One Model, Every Surface" tutorial — the natural `task::STATUS.eq(TaskStatus::InProgress)` had to be downgraded to `.eq("in_progress")` and a prose claim about compile-checked status filtering retracted because it wasn't true)

**SHIPPED** (commit `efde7982`, non-breaking variant). The `Choices` derive now emits `impl From<Enum> for String` that serializes through `ChoiceField::as_str` — the exact mapping the write path uses — so the existing `StrCol::eq<S: Into<String>>` / `ne` accept the enum variant directly: `status::STATUS.eq(TaskStatus::InProgress)` compiles and binds `'in_progress'`, single-sourced with `#[choices(rename_all = ...)]`.

Design decision (chosen with the maintainer): the **non-breaking** approach over the enum-only `ChoiceCol<M, E>` that the original proposal implied. Trade-off — the string form (`.eq("in_progress")`) still compiles, so a typo'd string is *not* a compile error (it matches no rows, as before). This kept zero churn: no call sites in the workspace, `examples/shop`, or the live `umbral_website` had to change. Within the workspace, `umbral-tasks.status` is a plain `String` (not choices), so nothing there was affected either way.

Test: `crates/umbral-core/tests/choices_typed_filter.rs` — seeds rows via the typed write path (enum status), then asserts `ticket::STATUS.eq(TicketStatus::InProgress)` selects the right rows, matches the `.eq("in_progress")` string form, `.ne(variant)` works, and a create→filter round-trip reads the enum back. Doc: `documentation/docs/v0.0.1/orm/column-types.mdx` updated to lead with the typed form (was documenting the old string-only limitation).

`.in_([E])` was in the original proposal but `StrCol` has no `in_` method at all (only `IntCol`/`UuidCol` do), so choices-column `in_` remains a separate, pre-existing gap — out of scope here.

50. **Slash-redirect is on, but some URLs still don't redirect.** (Reported live 2026-08-02.) **SHIPPED.** `slash_redirect_probe` replaces `slash_redirect_fallback`: a middleware layer wrapped around the WHOLE router (matched handlers, wildcard captures, nested services, and the fallback alike). Run the request; if the response is a 404 and the policy yields an alternate slash form, probe a pre-layer snapshot with a header-less GET and 308 when it answers (405/401/3xx count as "exists"). A 404 whose alternate ALSO 404s — a missing row with both slash forms registered, an out-of-scope row — passes through with its ORIGINAL body untouched, so REST's JSON 404s survive. Phase 5.6 now always installs the plain 404-rendering fallback when needed and applies the layer separately; 404 bodies are byte-identical to before in every case.
